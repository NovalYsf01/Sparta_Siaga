# SPARTA SIAGA Audit 001

Date: 2026-10-22
Mode: after
Scope: report details, operational actions, PIC assignment, HO visibility, Final Approval, and Case Close

## Findings

1. **HIGH: Report Details controls are too small and lack explicit keyboard focus styling.** The header icon buttons use compact padding, and the tab buttons do not provide a visible `focus-visible` treatment. This misses the 44 px touch target and keyboard focus requirements. Rules: R-03, R-32.

2. **MEDIUM: Ringkasan repeats status and workflow information across nested cards.** The header status, PIC banner, operational status panel, inspection panel, approval panel, and embedded completion card compete at the same visual level. Simplify Ringkasan to the current status, report identity, PIC, key dates, and short verification summary. Move the full workflow record to Riwayat. Rules: R-05, R-14, R-31.

3. **LOW: The second tab label does not match the requested information architecture.** The UI renders `Dokumen`, while the required read-only tabs are `Ringkasan`, `Dokumentasi`, and `Riwayat`. Rule: R-20.

4. **HIGH: PIC assignment is still a manual and mutable workflow.** The shared queue exposes Ambil Tugas, Tunjuk PIC, Alihkan PIC, Lepas PIC, and self-release controls. The PIC API supports POST, PATCH, and DELETE, while the assignment service writes ASSIGN, TRANSFER, and RELEASE history. This conflicts with automatic assignment to the first eligible BMS or BES who completes a valid persisted operational action, followed by immutability. Rule: R-26.

5. **HIGH: HO visibility is not enforced consistently at evidence boundaries.** Progress and readiness evidence routes grant every HO-scoped account national access without applying `canViewReport` or `isReportVisibleToHo`. An HO user can therefore request evidence for a manual report before initial BnM approval if the report and storage key are known. Rules: R-26, C-4.

6. **HIGH: Report authorization is duplicated instead of enforced through one policy at every boundary.** List, history, export, PDF, inspection evidence, progress evidence, readiness evidence, milestones, and completion routes use different combinations of SQL predicates, synchronous checks, and asynchronous permission checks. The duplicated policy can drift and does not provide one verified rule for manual-report gating, automatic-earthquake visibility, verification status, and branch isolation. Rules: R-26, R-35, C-4.

7. **HIGH: Final Approval and Case Close are separate in state but not atomic or concurrency-safe.** Each operation independently updates the approval row, inserts history, updates the incident, and attempts an audit insert. There is no transaction, row lock, or compare-and-set status predicate. Concurrent requests can create duplicate history or leave approval, incident, and audit state inconsistent. Audit insertion failures are caught and ignored. Rules: R-26, R-35, C-2.

8. **MEDIUM: Permission-aware stage actions are scattered and not represented by one stage-action contract outside Report Details.** Operational Report Center exposes progress actions, the shared queue exposes PIC mutations, and other stage actions use separate entry points. A single server-derived action descriptor should determine which external action is visible and enabled for the current role and stage. Rules: R-05, R-31.
